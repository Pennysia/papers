\section{Execution}\label{sec:execution}

The execution layer coordinates settlement within the terms authorized by the user.

\subsection{Signature-first order flow}\label{sec:signature-flow}

The user reviews the worst acceptable output (\textbf{WAP}, the minimum received after fees) and signs a typed-data order binding the input and output assets, output floor, deadline, and recipient (Appendix~\ref{app:order}). The network arranges the required transactions and gas payment.

\subsection{The three rails}\label{sec:rails}

Orders settle over three rails (Figure~\ref{fig:rails}).

\textbf{Atomic routes.} On a single chain, a Settlement-class router uses the signed allowance to pull the input and attempt ranked venues within one transaction. Execution stops at the first successful fill and reverts fully if all routes fail. This extends the prototype's production model to other EVM chains.

\textbf{Intent rails.} An intent settlement network matches the signed order with a filler that pays gas and delivers the specified output on the destination chain. Settlement is conditional on meeting the order's terms; an unfilled intent expires unpaid.

\textbf{Venue rails.} External venues use escrow contracts, where atomic exchange is possible~\cite{atomicswaps}, or deposit-address settlement with asynchronous delivery. The latter follows the prototype's privacy-swap integration and introduces counterparty exposure during settlement. Each quote discloses this model, and completion is reconciled against the signed terms (Section~\ref{sec:risk}).

\subsection{Guarantees and failure}

A successful fill must deliver at least the signed minimum before the deadline. For order $o$ signed by user $u$, the settlement condition is

\begin{equation}
\mathrm{settled}(u, o) \;\Longrightarrow\; \mathrm{delivered}(u, o) \geq \mathrm{WAP}(o) \;\land\; t \leq \mathrm{deadline}(o)
\end{equation}

\noindent Failure handling depends on the rail. Atomic execution reverts, unfilled intents expire, and deposit-address settlement requires a refund if delivery fails. That refund depends on the venue's settlement arrangements and carries the counterparty risk described in Section~\ref{sec:risk}. Table~\ref{tab:guarantees} summarizes the execution requirements.

To match the responsiveness users expect from a centralized exchange, the design targets execution within a few seconds of receiving the signed order, down to sub-second execution where the venue and rail support it. Execution latency is measured from signed-order receipt to a verified fill, with blockchain finality tracked separately. Same-chain atomic fills depend on block inclusion, while cross-chain and asynchronous venue settlement may take longer. Quotes disclose the expected completion time for the selected rail, and order status distinguishes execution from final settlement.

Executors deploy per-chain Settlement contracts or share an intent-native architecture; deployment and audit scope follows the approach chosen for each rollout.
